# 简析智评 V2.0 技术汇报与比赛答辩技术文档

> 文档用途：技术汇报、现场演示和比赛答辩底稿。本文以当前代码、配置和赛前冻结材料为准；探索性训练结果不作为平台泛化准确率。

## 技术摘要

简析智评 V2.0 采用 Vue 3 与 FastAPI 构建前后端分离平台，通过 DOCX/PDF/OCR 文档接入、规则分节、结构化抽取、六维评分、岗位语义匹配、证据护栏和优化稿生成，完成从简历上传到报告交付的完整流程。平台支持游客、学生、教师和管理员角色，具备单份与 ZIP 批量分析、SSE 实时过程、历史版本比较、岗位库、模拟面试、班级统计和 Word/PDF 报告功能。

项目的核心技术路线不是让一个大模型直接决定分数，而是将能力拆分为“语义理解、证据护航、生成交付”三擎：语义能力负责简历与岗位的相关性排序；规则层负责学历等硬约束、关键词证据、低信噪比和可信度控制；生成层负责把诊断转化为优化稿、报告和面试训练。云端模型是可选增强，未配置时主链路仍可本地运行。

主验收采用分层口径：59 份样本用于证明链路可运行；无 OCR 基线约 55.9% 的文本可读率说明扫描 PDF 必须进入 OCR；A 池前 15 条脱敏样本经双人标注和第三方裁决后，板块识别 micro F1 为 0.9785。三项指标分别说明可交付、可读取和可采信程度，不能合并成一个“平台准确率”。

## 1. 项目定位

简析智评是一套面向高校学生就业场景的简历诊断与求职成长平台。系统把学生端的简历分析、岗位适配、优化稿交付，与教师端的班级共性问题统计、训练任务生成连接起来，形成“学生诊断 → 教师洞察 → 岗位与简历质量沉淀”的就业数据治理闭环。

系统的核心交付不是一段聊天回复，而是一份可复核的分析结果和一份基于原始简历生成的优化稿。每个重要结论尽量关联到简历原文、识别板块、岗位关键词或硬约束；证据不足时提示低可信度、告警或封顶，而不是继续输出一个看似精确的高分。

## 2. 解决的问题

传统简历修改通常有三个问题：一是只能判断文件是否上传成功，不能区分文本没有读出来还是简历内容本身较弱；二是建议比较泛，缺少岗位要求、命中证据和缺失项；三是学生得到建议后仍需手工整理，教师也难以看到班级层面的共性短板。

本项目针对这三个问题设计了三层结果：

| 层次 | 系统回答的问题 | 主要输出 |
|---|---|---|
| 链路层 | 文件是否被成功处理 | 解析状态、实时事件、处理记录 |
| 可读层 | 系统是否读到了足够正文 | 文本可读性、版式复杂度、OCR 状态、质量告警 |
| 可信层 | 当前评分和建议是否有足够证据 | 六维分数、证据覆盖、置信度、低信噪比提示、优化建议 |

这三层不能合并成一个“准确率”。链路成功不等于文本可读，文本可读也不等于板块识别和岗位评价完全正确。

## 3. 总体架构

项目采用“简析智评三擎”架构：

```text
用户上传简历 / ZIP / 输入岗位或 JD
                  |
                  v
       文档接入与解析层
  DOCX / PDF / OCR / 分节识别 / 结构化抽取
                  |
                  v
       证据护航引擎
  六维规则评分 / 低信噪比 / 硬约束 / 可信度分层
                  |
                  v
       语义理解引擎
  岗位画像 / 关键词覆盖 / 同义扩展 / 语义相似度排序
                  |
                  v
       生成交付引擎
  诊断 / 修改建议 / 优化稿 Diff / Word/PDF 报告 / 模拟面试
                  |
                  v
       学生端与教师端
  历史版本 / 批量分析 / 班级统计 / 训练任务 / 管理配置
```

三擎的职责边界如下：

| 引擎 | 当前实现 | 职责边界 |
|---|---|---|
| 语义理解 | 分词与同义扩展；可选本地句向量模型 | 判断简历和岗位的语义相关性，服务岗位排序 |
| 证据护航 | 规则评分、岗位关键词、分节证据、学历等硬约束、低信噪比策略 | 判断结论是否有依据，发现风险并解释缺口 |
| 生成交付 | 本地规则模板、STAR 改写、可选云端大模型增强 | 把诊断转成优化稿、报告、面试题和行动路径 |

DeepSeek 只是生成交付引擎的可选云端实现，不是系统的唯一核心，也不应对外表述为“DeepSeek 引擎”。未配置 Key、网络不可用或解析质量过低时，主链路仍可使用本地规则和语义能力完成分析。

## 4. 一次分析的处理流程

### 4.1 文件接入

后端通过 FastAPI 接收 `.docx`、`.pdf` 和 `.zip`。上传层校验后缀、文件大小和压缩包解压路径，避免异常文件进入后续流程。ZIP 任务会逐份处理，并保留批量任务状态、成功数、跳过数和失败原因。

### 4.2 正文读取与 OCR

- DOCX：读取段落和表格文本。
- 可复制文本 PDF：提取原生文本。
- 扫描版或图片型 PDF：调用可选 PaddleOCR，识别中文正文。
- 解析失败：保留失败原因，不伪造正文或分析成功。

解析结果会记录原始文本、文本行、板块、解析质量、告警、版式复杂度和证据覆盖情况。前端通过 SSE 展示“正在读取、发现板块、命中关键词、低信噪比”等中间事件，便于演示和复核。

### 4.3 分节识别与结构化抽取

解析器将简历归一化为 `basic_info`、`education`、`internship`、`projects`、`campus`、`skills`、`awards`、`summary` 等板块，同时兼容常见中文标题和部分英文标题。

结构化抽取进一步形成教育经历、实习/项目经历、技能、证书和获奖等实体，并计算经历月份、量化表达数量、动作词、结果词、模糊表达和缺失板块。抽取结果服务于评分、岗位证据和优化稿，不把未识别内容当作用户没有经历。

### 4.4 六维评分与可信度

当前评分维度为：

1. 内容完整性
2. 经历相关性
3. 语言专业性
4. 格式规范性
5. 亮点量化程度
6. 岗位语义匹配

评分引擎同时输出分项分数、综合分数、证据摘要、问题诊断和可信度状态。低信噪比策略重点检查经历是否只有职责没有结果、是否缺少量化指标、是否存在过度泛化表达、是否存在异常长句，以及正文是否不足。

当正文提取不足时，系统将结果标为低可信度并限制增强分析；这相当于把“机器没读懂”与“简历内容较弱”分开处理。版式复杂度用于提醒复核，不单独等价为简历质量差。

### 4.5 岗位匹配

岗位匹配包含四类信息：岗位画像、关键词覆盖、语义相似度和硬约束。

- 岗位画像：从本地岗位库或岗位模板中取得技能、职责和关注点。
- 关键词层：做同义词扩展和命中/缺失统计，并定位命中所在板块。
- 语义层：在可用时使用本地句向量模型计算简历与岗位文本相似度，语义分作为主排序分。
- 规则层：负责学历等硬约束、关键词证据和缺口解释；硬约束失败时可以直接拦截语义排序。

没有填写目标岗位时，系统只做通用分析并推荐相似岗位，不会把简历中的求职意向静默套用成用户的目标岗位。用户填写 JD 但没有填写岗位名时，系统按 JD 分析，不自动改写岗位名。

### 4.6 生成交付

系统根据初稿证据生成结构化诊断、修改方向、行动路线和优化稿预览。优化稿遵循两条约束：

- 不编造原简历中不存在的经历、数字和结果。
- 证据不足的位置标记“待补充”，并展示初稿与优化稿 Diff。

结果可导出 Word/PDF 报告，也可进入模拟面试模块。云端大模型只负责可选的语言增强，失败时回退到本地结果。

## 5. 工程实现

| 层次 | 技术与目录 | 主要职责 |
|---|---|---|
| 前端 | Vue 3、Vite、ECharts | 上传、分析流、详情、报告、批量、岗位库、教师统计和面试页面 |
| 后端 | Python、FastAPI | API、会话、权限、任务调度、分析编排和报告下载 |
| 文档处理 | python-docx、PDF 文本解析、可选 PaddleOCR | 正文、表格和扫描 PDF 接入 |
| 分析服务 | `parser.py`、`structured_extract.py`、`score_engine.py`、`match_engine.py` | 分节、实体、评分、匹配和证据解释 |
| 语义服务 | `semantic_match.py`、本地 IDF、同义词库和可选句向量权重 | 语义相似度和岗位排序 |
| 交付服务 | `optimized_resume.py`、`resume_rewriter.py`、`report.py`、`interview_engine.py` | 优化稿、Diff、报告和面试训练 |
| 数据层 | SQLAlchemy；支持 MySQL，测试和本地轻量环境可用 SQLite | 用户、分析记录、岗位、报告和批量任务持久化 |
| 异步能力 | SSE 实时事件；FastAPI BackgroundTasks；可选 Celery/Redis | 展示分析过程，执行后台增强和批量任务 |

后端主入口为 `backend/app/main.py`，分析编排集中在 `backend/app/services/analysis_pipeline.py`。前端通过 `frontend/src/api/client.js` 调用后端 API，页面按单份分析、批量分析、历史记录、岗位库、面试和教师端组织。

### 5.1 前端页面与用户角色

前端使用 Vue Router 管理工作台页面，并在路由层进行基础角色判断。主要页面如下：

| 页面 | 面向角色 | 主要功能 |
|---|---|---|
| 工作台首页 | 游客、学生、教师、管理员 | 最近分析、功能入口和平台状态 |
| 单份分析 | 游客、学生 | 上传简历、选择是否套用岗位、查看实时分析过程 |
| 批量分析 | 游客、学生、教师 | 上传 ZIP、查看逐份进度和汇总结果 |
| 简历记录与详情 | 游客、学生 | 查看历史、版本差异、岗位依据、优化稿和报告 |
| 模拟面试 | 学生 | 根据目标岗位和简历证据生成问题与训练建议 |
| 岗位库 | 学生、教师、管理员 | 筛选岗位、复制岗位模板、查看适配依据 |
| 教师看板 | 教师、管理员 | 班级均分、分布、高频短板、学生记录和训练任务 |
| 管理后台 | 管理员 | 用户、岗位、评分模板、AI 配置、审计日志和存储清理 |

游客通过 HttpOnly 的访客会话 Cookie 隔离历史记录；注册或登录后可以导入访客历史。教师和管理员页面不仅依赖前端路由守卫，后端接口还会再次校验角色和资源归属，前端限制不被当作真正的安全边界。

### 5.2 后端分层

后端按职责拆分为以下层次：

```text
API 路由层
  接收参数、校验文件、解析当前用户、返回 HTTP/SSE 响应
        |
        v
平台编排层
  创建记录、选择同步/后台/流式任务、控制版本与资源归属
        |
        v
分析服务层
  文档接入、解析、评分、匹配、优化、报告和面试
        |
        v
数据访问层
  SQLAlchemy 实体、会话、运行时建表与兼容字段升级
        |
        v
文件存储层
  uploads / extracted / reports，并执行受限删除
```

这种划分让算法服务可以在 API 之外被测试脚本直接调用，也让批量任务、实时任务和普通上传复用同一条分析主链路，减少“演示接口一套逻辑、评测脚本另一套逻辑”的风险。

### 5.3 主要 API

所有接口统一挂载在 `/api` 下。答辩时不必逐条背诵，但应能说明系统不是前端静态演示，而是具有完整业务接口。

| 接口组 | 代表接口 | 作用 |
|---|---|---|
| 健康检查 | `GET /api/health` | 检查数据库、Redis 和任务执行模式 |
| 单份分析 | `POST /api/resumes/analyze` | 上传 DOCX/PDF，创建分析记录并选择流式或后台执行 |
| 直接分析 | `POST /api/resumes/analyze-direct` | 接收 Base64 文件内容，便于客户端集成 |
| 批量分析 | `POST /api/resumes/analyze-zip` | 创建 ZIP 批量任务 |
| 实时过程 | `GET /api/history/{id}/analysis-live` | 执行真实分析并通过 SSE 推送事件，完成后落库 |
| 历史与版本 | `GET /api/history`、`GET /api/history/{id}/versions`、`GET /api/history/compare` | 查询记录、版本链和分数变化 |
| 岗位应用 | `POST /api/history/{id}/apply-job` | 将推荐岗位应用到已有简历，生成新版本分析 |
| 优化与面试 | `POST /api/history/{id}/rewrite-preview/refresh`、`POST /api/history/{id}/interview-prep/refresh` | 按需刷新优化稿和面试准备 |
| 报告与原件 | `GET /api/history/{id}/report/download`、`GET /api/resumes/{id}/source` | 下载分析报告或授权范围内的源文件 |
| 身份认证 | `/api/auth/register`、`/api/auth/login`、`/api/auth/logout`、`/api/auth/me` | 注册、登录、退出和当前身份 |
| 岗位管理 | `/api/job-market`、`/api/job-profiles` | 岗位检索和个人岗位画像管理 |
| 教师端 | `/api/teacher/stats`、`/api/teacher/classes`、`/api/teacher/training-tasks` | 统计班级问题并生成教学任务 |
| 管理端 | `/api/admin/users`、`/api/admin/score-config`、`/api/admin/ai-config` | 用户、评分模板和 AI 配置管理 |

### 5.4 核心数据实体

数据库不是只保存一个总分，而是把身份、文件、分析版本、岗位和报告拆分保存。

| 实体 | 关键字段 | 作用 |
|---|---|---|
| `User` | 用户名、密码哈希、角色、状态、最后登录时间 | 支持学生、教师和管理员身份 |
| `UserProfile` | 学校、专业、年级、班级 | 支持教师端分组统计 |
| `AnalysisRecord` | 文件名、目标岗位、六维分、板块、诊断、建议、匹配结果、状态 | 一次分析的核心业务记录 |
| `BatchTask` | 文件总数、成功/失败/跳过数、任务状态 | 管理 ZIP 批量分析进度 |
| `UploadedFile` | 原文件名、存储路径、文件类型、大小 | 将物理文件与分析记录关联 |
| `Report` | 报告类型、格式、存储路径 | 管理 Word/PDF 输出 |
| `JobProfile` | 岗位名称、类别、描述、要求摘要 | 保存用户或教师使用的岗位画像 |
| `AuditLog` | 操作者、动作、目标、IP、结果 | 记录管理操作，便于追踪 |

`AnalysisRecord` 通过 `root_record_id`、`parent_record_id` 和 `version_no` 构成版本链。用户修改简历或应用新岗位后，系统生成新记录，而不是覆盖旧结果，因此可以计算总分和分项分的变化，并保留前后证据。

JSON 字段用于保存结构变化较快的分析结果，例如分节内容、诊断、建议、匹配解释和前端扩展数据；关系字段用于用户、文件、批次、岗位和版本的稳定关联。

### 5.5 任务执行机制

系统提供三种执行方式：

| 模式 | 适用场景 | 实现 |
|---|---|---|
| SSE 实时分析 | 比赛演示和单份交互 | 后台线程执行真实 pipeline，事件队列逐条推送，完成后落库 |
| 进程内后台任务 | Windows 本地体验、未启用 Celery | FastAPI BackgroundTasks 执行 |
| Celery 异步任务 | Docker 或多人部署 | Redis 作为 broker/backend，Celery Worker 执行 |

实时流中的典型事件包括 `extract`、`parse_line`、`section_found`、`structured`、`keyword_hit`、`keyword_miss`、`semantic`、`low_snr` 和 `done`。这些事件来自真实分析回调，不是前端伪造进度条。

批量分析先安全解压 ZIP，再按文件逐份复用单份分析能力。离线分析的并行度可配置为 1 到 4；开启云端 AI 时并发上限进一步收紧，降低接口限流和费用风险。任务每处理若干文件提交一次进度，并支持暂停和重试。

### 5.6 文件生命周期

文件分别存放在：

- `data/uploads/`：原始上传文件。
- `data/extracted/`：ZIP 解压出的临时文件。
- `data/reports/`：生成的 Word/PDF 报告和优化稿。

删除历史记录时，会清理关联文件和报告。删除服务会先解析目标路径，并只允许删除上述受控目录中的文件，避免把数据库里的异常路径扩展为任意文件删除。

ZIP 解压会检查路径穿越、允许的文件类型和解压总大小。压缩包中不支持的文件会被记录为跳过，而不是导致整个任务静默失败。

### 5.7 配置管理

主要配置来自根目录 `.env`：

| 配置 | 作用 | 演示建议 |
|---|---|---|
| `DATABASE_URL` | SQLAlchemy 数据库连接 | 现场提前验证连接；轻量环境可用 SQLite，当前项目配置也可连接 MySQL |
| `DEEPSEEK_API_KEY` | 可选云端增强 | 无 Key 仍可运行；演示真实简历时建议关闭外传 |
| `USE_SEMANTIC_MATCH` | 启用语义匹配 | 保持开启，至少可使用本地分词语义基线 |
| `USE_SEMANTIC_MODEL` | 启用句向量模型 | 仅配合明确的本地 `SEMANTIC_MODEL_PATH` 使用 |
| `SEMANTIC_BLENDER_PATH` | 加载实验融合器 | 默认不配置，避免误用同源拟合权重 |
| `USE_CELERY` | 使用 Celery/Redis | 本地演示可关闭，Docker 部署可开启 |
| `MAX_UPLOAD_SIZE_MB` | 单文件大小上限 | 默认 20 MB |
| `MAX_ZIP_TOTAL_SIZE_MB` | ZIP 解压总量上限 | 默认 120 MB |
| `SESSION_SECRET` | 会话签名密钥 | 正式部署必须更换随机强密钥 |

系统对生产环境配置有额外检查，例如不允许继续使用默认会话密钥和弱管理员密码；HTTPS 部署时应开启 Secure Cookie，并根据学校使用范围决定是否关闭公开注册。

## 6. 核心算法与评分逻辑

### 6.1 默认权重

综合分使用六个维度的加权和：

```text
总分 = Σ（分项得分 × 对应权重）
```

默认权重为：内容完整性 20%、经历相关性 20%、语言专业性 15%、格式规范性 10%、亮点量化程度 15%、岗位匹配 20%。系统还内置数据分析、产品经理、前端开发、后端开发和新媒体运营等岗位模板。例如开发岗位提高岗位匹配权重，新媒体岗位提高亮点量化权重。

岗位权重模板属于可解释的工程策略，不应表述为经过全国学生群体统计验证的标准量表。管理员可以选择运行时模板，但正式比较不同学生或班级时应固定模板和版本，避免口径漂移。

### 6.2 六维分数的证据来源

| 维度 | 主要证据 | 典型扣分或限制因素 |
|---|---|---|
| 内容完整性 | 基本信息、教育、实习、项目、技能、获奖、校园板块 | 核心板块缺失、正文不足 |
| 经历相关性 | 经历行数、动作词、结果词、量化指标、实习与项目组合 | 只有职位名称、没有职责结果、无有效经历正文 |
| 语言专业性 | 动作词、结果词、模糊词、长句 | “比较、很多、较强”等泛化表达，句子过长 |
| 格式规范性 | 文本行数、平均行长、板块数量、联系方式和日期 | 内容过少、粘连长行、板块结构不足 |
| 亮点量化程度 | 数字、比例、人数、金额、增长率、成果词 | 没有量化证据或结果闭环 |
| 岗位匹配 | 语义相似度、岗位关键词、分节命中、硬约束 | 缺少核心技能、学历要求不符、没有目标岗位 |

系统不会要求所有内容都量化。例如教育行、技能清单、证书和职位名称不会被统一当成“缺少数字”的低信噪比经历；低信噪比主要针对应当描述行动和结果的项目、实习与校园实践正文。

### 6.3 解析质量状态

解析质量分为 `high`、`medium` 和 `low`：

- `low`：正文为空、正文短于约 80 字、核心板块命中不超过 1 个，或噪声比例过高。
- `medium`：正文较短、核心板块不足、有 OCR 或其他需要复核的告警。
- `high`：正文长度、教育、经历、技能/项目等结构较完整，且噪声较低。

当解析质量为 `low` 时，每个分项最高限制为 62 分，综合分最高限制为 58 分，并标记 `low_parse_capped`。这个封顶不是说简历真实水平最多 58 分，而是说机器当前没有足够证据支持更高分。

### 6.4 证据覆盖与可信度

没有目标岗位时，证据覆盖主要看教育、实习、项目和技能四个核心板块的识别比例。有目标岗位时，还会结合岗位关键词覆盖和证据置信度：

```text
证据覆盖 ≈ 核心板块覆盖 × 0.5
         + 岗位匹配覆盖 × 0.3
         + 证据置信度 × 0.2
```

当证据覆盖低于 0.5 时，结果标记为 `evidence_review`；当版式复杂度达到复核阈值时标记 `layout_review`；正文过低则标记 `low_parse_capped`。这些状态用于提醒用户“结论需要人工核验”，而不是把复杂版式直接扣成低质量简历。

### 6.5 语义匹配实现

语义通道有两级回退：

1. 显式启用并提供本地模型路径时，使用 sentence-transformers 生成归一化向量并计算余弦相似度。
2. 模型不可用时，使用 jieba 分词、技能同义词归一、IDF 加权词向量和余弦相似度。

当前岗位匹配策略不是直接采用 `规则分 × α + 语义分 × (1-α)` 作为线上主分。代码中的主策略是：硬约束失败则拦截；语义可用时采用语义分作为主排序，规则层提供证据和缺口；语义不可用时回退规则分。融合器函数和实验权重仍保留用于研究，但只有显式指定路径才会加载。

### 6.6 硬约束与安全处理

学历等条件属于硬约束。系统将其输出为 `pass`、`fail` 或 `unknown`：

- `pass`：简历中有明确证据满足要求。
- `fail`：简历中有明确证据不满足要求，可以阻断语义排序。
- `unknown`：简历没有足够证据，不按失败处理，也不伪造满足。

这种三值逻辑比简单二元判断更适合简历场景，因为“没有写”不一定等于“没有”。

### 6.7 诊断与优化稿生成

诊断引擎将问题组织为“问题—证据—方向—示例”四元结构。优化稿以原始文本为基线，优先做动作词增强、STAR 结构整理、结果前置和岗位关键词对齐。对于原文没有的数据，系统只能给出填写位置或“待补充”，不能自动生成虚假数字。

云端增强请求会受到两项保护：解析质量为低时直接跳过；大批量任务超过设定数量时自动使用规则结果，以避免把不可读文本发送到模型或造成批量延迟。云端返回还需要通过 JSON 解析、字段完整和禁止编造等约束，失败后保留离线结果。

## 7. 数据治理与安全

真实简历只在本地处理，不进入 Git、Prompt、训练集或对外分享包。对外评测材料使用脱敏文本、匿名 ID 和标注工具；姓名、电话、邮箱、身份证号等敏感字段不写入评测 JSON、报告或日志。

评测数据按用途分为：

| 数据池 | 用途 | 限制 |
|---|---|---|
| A 池 | 清晰样本、解析评测和裁决 | 双人独立标注，分歧保留裁决记录 |
| B 池 | 复杂版式和能力边界 | 用于发现失败模式，不用于刷指标 |
| C 池 | 现场演示 | 不进入训练和正式测试 |

真实简历标注主要用于解析评测、边界发现、示例筛选和可信度验证，不默认用于模型训练。小样本语义训练和融合权重拟合如果与评测数据同源，只能作为探索性附件，不能包装成独立泛化结论。

### 7.1 数据处理边界

真实简历从进入项目到形成评测材料，需要经过以下流程：

```text
原始真实简历（本地、受控、禁止提交）
             |
             v
字段级脱敏与人工复核
  姓名 / 手机 / 邮箱 / 身份证号 / 学校等敏感信息清理
             |
             v
生成匿名 TXT 与稳定样本 ID
             |
             v
按 A / B / C 池分拣
             |
             +---- A 池：双人独立标注、裁决、解析评测
             +---- B 池：复杂版式、失败类型和能力边界
             `---- C 池：脱敏演示，不进训练与正式测试
```

PDF 脱敏尤其需要谨慎：项目不尝试只改 PDF 文本层后继续对外发送原文件，因为扫描图片中的姓名和联系方式可能仍然存在。PDF 默认只导出脱敏 TXT 供评测；DOCX 即使改写段落和表格，也要注意文本框可能残留，因此最终以人工检查后的脱敏 TXT 为准。

### 7.2 双人标注与裁决

两名标注员应使用同一批稳定样本 ID 独立完成标注，结果分别保存，在提交前不能查看对方标签。比对后产生的分歧不直接用多数投票消失，而是形成裁决工作表，由负责人依据统一规则逐项给出最终标签和裁决理由。

项目中 A 池前 15 条经历了双人初标和第三方裁决。初始一致性不高并不代表系统失败，反而说明“板块是否存在”的人工标准原本存在歧义。先统一标签定义、再裁决、最后计算 F1，比直接选择对系统有利的标签更符合数据治理要求。

### 7.3 外部模型调用

只有同时满足以下条件，简历文本才会发送到配置的云端模型接口：

1. `.env` 中存在有效 API Key。
2. 用户在前端开启增强分析。
3. 解析质量不是 `low`。
4. 当前任务未因批量规模触发本地回退。

完全本地处理时，应关闭前端增强开关或留空 API Key。答辩中不能简单说“系统绝不会外传”，正确表述应是：“主链路支持完全本地运行；只有用户主动开启并配置云端服务时才会调用外部接口。”

### 7.4 身份、权限与审计

密码使用哈希保存，登录后通过 HttpOnly Cookie 维持会话。用户只能访问自己或当前访客会话拥有的记录；教师和管理员接口进行后端角色校验。管理员修改用户角色、状态、AI 配置和评分配置等操作写入审计日志。

正式上线还应补充学校级的数据保留周期、用户授权文本、撤回机制、备份加密、访问审批和第三方 API 数据处理协议。当前竞赛系统可以证明有基本技术保护，但不能替代学校正式的信息安全和个人信息保护制度。

## 8. 测试、验收与指标口径

### 8.1 测试体系

后端测试覆盖解析、评分、匹配、语义回退、低信噪比、异步分析、实时流、批量任务、ZIP 安全、报告、版本、岗位库、教师端和数据库结构。测试分为四类：

| 类型 | 目的 | 示例 |
|---|---|---|
| 单元测试 | 验证函数和规则边界 | Java 不误命中 JavaScript、无目标岗不虚高、学历 unknown 安全处理 |
| 服务测试 | 验证模块组合 | 解析后评分、优化稿生成、岗位证据定位 |
| API/流程测试 | 验证记录创建、实时流、后台增强和历史版本 | 单份分析、SSE、重试、应用推荐岗位 |
| 验收脚本 | 生成固定口径的聚合指标和报告 | 平台能力验收、真实标注评测、OCR 探测 |

代码测试证明实现没有因修改发生已知回归，真实脱敏样本评测用于说明能力边界，两者不能互相替代。

### 8.2 主验收三层指标

赛前冻结材料给出的主答辩口径如下，必须带着样本范围和证明对象一起说：

| 层级 | 冻结结果 | 能证明什么 | 不能证明什么 |
|---|---:|---|---|
| L1 链路 | 59 份分析成功率 100%；合成解析 20 条 F1=1.00；护栏 4/4 | 主链路可运行、可交付、护栏按预期工作 | 不能直接证明真实简历解析准确 |
| L2 可读 | 59 份无 OCR 基线可读率约 55.9%；其中 26 份 PDF 原生文本为空；OCR 抽样 26/26 可读 | 扫描 PDF 必须进入 OCR 分支 | 不能把可读率叫作解析准确率 |
| L3 可信 | A 池前 15 条双人标注后经裁决，板块 micro F1=0.9785，P=0.9681，R=0.9891 | 脱敏裁决样本上的板块识别能力 | 不能外推为字段级准确率或全库泛化 |

薄弱边界要主动说明：裁决样本中 `projects` 板块 F1 约 0.8333，`awards` 约 0.90，复杂版式和板块边界仍可能混淆。系统的处理方式是告警、降低可信度或限制增强，而不是强行给出确定结论。

匹配实验中存在 61 条弱标注数据与训练/拟合过程同源的情况，因此相关 SBERT、融合权重和 Spearman 数字只作为探索附录。主答辩不把它们称为平台泛化准确率，也不把当前实验模型包装成独立测试结论。

### 8.3 性能结果

59 份无 OCR 冻结批次中，单份 DOCX 基线 10 次的平均处理时间约 409 ms、P95 约 420 ms；20 次压力样本平均约 411 ms、P95 约 420 ms。并发测试中 2、4、8 个 Worker 均完成全部任务，8 Worker 任务耗时 P95 约 971 ms。

这些结果是在固定本地环境、规则主链路和指定样本上得到，只能说明该环境下的工程性能。OCR、云端 AI、句向量模型、数据库网络延迟和硬件差异都会改变耗时，因此答辩时不宜承诺所有部署环境都能达到同样速度。

### 8.4 指标公式

板块识别把每份简历的每个板块看作“存在/不存在”判断：

```text
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2 × Precision × Recall / (Precision + Recall)
```

micro F1 汇总所有样本和板块的 TP、FP、FN 后统一计算，适合观察整体板块检出表现。但它可能被高频、容易识别的板块主导，因此文档同时报告 `projects`、`awards` 等单板块结果和错误样本。

### 8.5 为什么不采用单一准确率

如果只报告“59 份成功率 100%”，评委无法知道 26 份扫描 PDF 当时是否真的读到正文；如果只报告“OCR 可读率 100%”，也无法证明教育、项目和技能板块被正确识别；如果只报告 15 条板块 F1，也不能证明整个上传、报告和批量链路稳定。因此本项目坚持分层汇报。

### 8.6 当前证据冲突风险

仓库中存在不同时间生成的验收 JSON：一个批次包含 59 份 DOCX/PDF，另一个后生成的结果只包含 33 份 DOCX。二者并不是同一次实验，不能把字段混合引用。正式提交或制作最终 PPT 前，应重新运行一次锁定版本的验收脚本，并统一以下内容：

- 代码提交版本或 Git Commit。
- 样本清单和匿名样本 ID。
- 是否启用 OCR、语义模型和云端 AI。
- 数据库、硬件、Python 和依赖版本。
- 生成时间、指标 JSON、DOCX 报告和 PPT 数字。

本文暂按 `docs/赛前收口完成.md` 指定的 59/26/15 冻结口径撰写，不把后续 33 份批次替换进主结论。

## 9. 异常处理与降级策略

| 异常 | 系统行为 | 用户可执行动作 |
|---|---|---|
| 扫描 PDF 无原生文字 | 尝试 OCR；未安装 OCR 时标记失败或低可读 | 安装 OCR 依赖或上传文字版 PDF/DOCX |
| DOCX 使用大量文本框 | 正文可能不足，标记解析告警并封顶 | 另存为标准 DOCX 或文字版 PDF |
| 云端 AI 无 Key、超时或返回异常 | 保留本地规则分析，标记回退状态 | 继续使用离线结果或稍后刷新增强 |
| 本地句向量模型不可用 | 回退到 jieba、同义词和 IDF 语义基线 | 不影响主链路 |
| Redis 不可用且 Celery 关闭 | 继续使用进程内后台任务 | 本地演示无需处理 |
| Redis 不可用且 Celery 开启 | 健康检查降级，异步任务不可用 | 恢复 Redis 或关闭 Celery |
| ZIP 含路径穿越或超限内容 | 拒绝危险条目并记录跳过/失败 | 重新整理 ZIP |
| 原文件被删除 | 记录置为失败并返回明确错误 | 重新上传简历 |
| 岗位库未命中 | 按用户填写岗位做通用匹配并保留推荐 | 补充 JD 或创建岗位画像 |
| 没有填写岗位 | 通用分析，岗位只推荐不自动采用 | 在结果页点选岗位生成新版本 |

降级策略的设计目标是“能力可以下降，但结论口径不能失真”。例如 OCR 不可用时不能伪造正文，语义模型不可用时必须标明规则回退，云端增强失败时不能丢掉已经生成的本地结果。

## 10. 现场演示脚本

建议控制在两分钟左右：

1. 进入“单份分析”，上传一份示例 DOCX，填写“数据分析实习生”等目标岗位。
2. 展示实时解析事件：正文读取、板块识别、岗位关键词命中和缺失。
3. 进入详情页，先看“链路—可读—可信”三层状态，再看六维评分和证据片段。
4. 展示岗位适配依据：命中技能、缺失技能、硬约束和推荐岗位；说明未填目标岗时不会自动套岗。
5. 打开初稿与优化稿 Diff，指出优化稿不编造经历，缺数字的位置会标“待补充”。
6. 下载 Word/PDF 报告；时间允许时展示批量分析或教师班级共性问题。

演示前确认 `.env` 中数据库可连接、前端和后端地址一致、示例文件不含真实个人信息；不要把真实学生简历直接用于现场演示。

### 10.1 两分钟讲解词

> 这是简析智评的单份分析页面。我先上传一份脱敏简历，并明确选择目标岗位。上传后显示的不是模拟进度，而是后端真实分析事件，包括正文读取、板块识别、关键词命中和语义匹配。进入详情后，我们先分开看链路是否完成、文本是否可读、当前结论是否可信，再看六维评分。岗位匹配由语义通道负责主排序，规则层负责学历等硬约束和证据解释。最后系统基于初稿生成优化稿，不能确认的数据标记待补充，并通过 Diff 让学生核对。结果还可以导出报告，教师端则汇总班级共性问题。

### 10.2 五分钟技术汇报结构

1. 用 30 秒说明问题：简历可能没读懂、建议缺证据、教师缺少班级视角。
2. 用 45 秒说明三擎架构及职责边界。
3. 用 60 秒演示真实分析流、三层可信度和岗位证据。
4. 用 45 秒展示优化稿 Diff、报告和教师端闭环。
5. 用 45 秒说明数据治理与 A/B/C 分池。
6. 用 45 秒说明 59/26/15 三层验收数字及其边界。
7. 用 30 秒主动说明 `projects` 板块、复杂版式和样本规模等局限。

### 10.3 演示失败备用方案

- 准备一份标准 DOCX 和一份扫描 PDF，两者都必须脱敏。
- 提前生成一条成功历史记录，即使现场上传失败，也能进入详情展示完整结果。
- 准备已导出的 Word/PDF 报告和优化稿。
- 无网络时关闭 AI 增强，使用本地规则和语义基线。
- OCR 依赖无法启动时先演示 DOCX，并通过冻结 OCR 结果说明扫描 PDF 能力。
- 数据库临时不可用时不要重复点击上传，应先检查 `/api/health`。

## 11. 评委常问问题与回答

### Q1：为什么不用一个大模型直接评价？

大模型适合语言生成，但不适合作为唯一评分依据。我们把规则、语义和生成拆开：规则负责硬约束和证据，语义模型负责岗位相关性排序，生成模块负责把结论转成可执行优化稿。这样既能离线运行，也能解释“为什么得分”和“缺什么证据”。

### Q2：测试集有没有参与 Prompt 或参数选择？

主平台验收采用冻结推理，不在测试集上重新拟合参数或 α。61 条匹配弱标注实验与训练/拟合同源，所以被降为探索附录；我们不会把它写成独立泛化指标。

### Q3：解析失败时如何区分简历差和机器没读懂？

系统先判断正文是否读到、版式是否复杂、证据覆盖是否足够，再决定评分可信度。正文为空或不足时标记低可读，不把空文本当成内容差；可读但缺少量化结果时，才进入简历内容诊断。

### Q4：规则和语义分数如何融合？

当前线上策略是语义分主排序，规则分不未经验证地和语义分简单加权。规则层提供关键词覆盖、分节命中、硬约束和解释；语义模型不可用时才回退到规则匹配。这样可以避免规则分污染语义排序，同时保留离线可用性。

### Q5：优化稿会不会编造经历？

优化稿以解析到的初稿和证据片段为输入，不允许凭空增加经历、数字或结果。无法从原文确认的地方标记“待补充”，并用 Diff 让用户逐项核对。

### Q6：教师端有什么价值？

学生端解决单份简历修改，教师端聚合班级评分分布、专业/年级/班级维度和高频问题，并可将共性问题转为训练任务。教师端只展示必要的统计和审核信息，不默认展示全班简历正文。

### Q7：项目的局限是什么？

当前局限包括：扫描 PDF 对 OCR 依赖较强，复杂版式仍可能出现板块边界混淆；岗位库覆盖和岗位 JD 质量会影响匹配解释；样本规模有限，不能宣称覆盖所有学校、专业和简历模板。下一步应扩大脱敏、多样化且严格隔离的评测集，再评估模型增强，而不是直接用小样本继续调参。

### Q8：六维评分的权重是谁定的，科学吗？

当前权重来自岗位场景和产品规则，是可解释、可配置的工程评分，不是国家职业测评标准。系统保存实际采用的权重模板，便于复现。下一阶段需要用更大规模、多专业、专家标注且严格隔离的数据做校准；在此之前，我们只把它用于诊断和相对改进，不宣称替代招聘决策。

### Q9：为什么解析板块 F1 很高，但还说有风险？

因为该 F1 来自 15 条脱敏、裁决后的板块“是否存在”评测，不是字段级抽取，也不是所有模板的泛化结果。总体 micro F1 较高，但项目板块仍有约 0.83 的 F1，所以系统保留版式和证据告警。

### Q10：OCR 后 26 份 PDF 都可读，是否说明 OCR 准确率 100%？

不能。26/26 只表示 OCR 输出了足够文本，属于可读率，不代表每个字、每个字段或每个板块都正确。OCR 文本仍需经过板块评测和人工抽查。

### Q11：语义模型是否真的上线？

系统始终有本地分词、同义词和 IDF 语义基线。句向量模型只有在显式配置本地模型路径时才启用。当前环境可以启用实验权重，但主答辩不使用同源弱标注上的训练数字证明泛化能力。

### Q12：系统能否用于自动淘汰学生或候选人？

当前定位是学生自我诊断和教师教学辅助，不应作为自动淘汰或录用决定。分数受解析、岗位库、规则和样本范围影响，系统必须保留人工复核和申诉空间。

### Q13：为什么要做版本链？

只展示一次得分无法证明建议是否有帮助。版本链保留每次简历修改和岗位变化，计算总分与分项变化，并让用户查看改动依据。它服务于成长过程，而不是覆盖旧数据。

### Q14：教师端是否会泄露学生简历？

教师端主要展示班级分布和共性问题，学生记录访问受角色和后端接口约束。正式学校部署还需依据组织关系限制教师可见班级，并实施数据最小化；当前竞赛版本不能把“有角色页面”夸大为完整校级权限体系。

### Q15：项目最大的技术创新是什么？

创新不在于单独调用某个大模型，而在于把语义排序、规则证据、可信度分层、优化稿交付和数据治理连接成可复核闭环：系统不仅给结论，还说明证据、能力边界和失败原因，并把结果沉淀为学生版本和教师统计。

## 12. 风险、局限与后续路线

### 12.1 当前风险

- 真实裁决样本只有 15 条，无法代表全部专业和版式。
- 扫描 PDF 的文字质量受图片分辨率、字体、双栏和背景影响。
- 六维权重是工程规则，尚未完成大规模专家一致性和效度研究。
- 岗位库覆盖有限，JD 本身含糊时，匹配证据也会受影响。
- 云端模型可能产生语言流畅但证据不足的内容，因此必须保留护栏和人工核对。
- 当前 `.env` 可能包含本机数据库和 API 配置，不能进入公开提交包或 Git。

### 12.2 推荐后续路线

1. 冻结现有测试集，新增学校、专业和版式来源不同的独立测试集。
2. 将解析评测从板块存在扩展到字段级实体、日期范围和经历归属。
3. 建立专家评分规范，评估六维分数的一致性、稳定性和实际指导价值。
4. 对岗位匹配建立严格的训练、验证、测试分组，再决定是否启用微调模型。
5. 为云端生成建立禁止编造率、结构合法率、建议可执行率和重复稳定性评测。
6. 完善校级多租户、班级授权、数据保留周期、加密备份和监控告警。

不建议下一步直接继续在 61 条同源数据上调 α 或追求更高 Spearman。更有价值的工作是扩大独立证据、统一验收版本和补齐字段级评测。
